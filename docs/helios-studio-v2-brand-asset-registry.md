# Brand upload registry adoption

Status: draft implementation following the Stream asset registry. No R2 object, credential, production database or deployment was changed.

Testimonial-photo and trusted-logo presign routes now register a server-generated company key before signing it. The direct logo-upload route registers identity before writing bytes. All three withhold success when the registry transition fails. Provider/signing failures mark pending records failed without deleting uncertain provider state. The underlying R2 credentials, adapter, public URL scheme and signing implementation remain unchanged.

The registry namespace contains the R2 account and bucket names, never access keys or tokens. The existing registry unique constraint prevents a duplicate key from being granted through another upload intent. Company/category prefixes remain a separate policy check. The registered object is provisioned, not certified as ready: attachment still performs the existing object-head check for a changed image. MIME, dimension, checksum and byte-size verification are future integrity gates; the stored size is client-declared.

Testimonial and logo create/update handlers now check registry owner and status before storage access. Unknown new keys fail in tenant mode, under the asset-ownership flag, or when multiple companies exist. Unknown old keys may be attached only by the sole matching company with enforcement disabled. Unchanged images on a scoped existing record remain compatible without an object-head round trip, but a foreign workspace prefix or known disallowed registry owner/status is rejected even then. Changing display text does not silently adopt or reassign historical assets.

No new schema migration is required beyond the preceding registry expansion. Existing photo/logo columns continue to store keys; asset usages are not yet represented by foreign keys. Cleanup remains deferred. Presigned URLs retain their existing five-minute lifetime and can still overwrite their own generated key while valid. They are bearer capabilities; this change does not introduce single-use URLs, replacement versions or a complete immutable-bytes lifecycle.

Local executable helper/handler tests cover registration before signing/writing, collisions, foreign/unknown/status rejection, failed provision recording, constrained legacy fallback, server-owned keys and viewer rejection. The preceding PGlite registry tests cover immutable identity and unique constraints. Actual browser uploads, hosted migration/application overlap, provider-header/file validation, historical reconciliation and lifecycle workers remain release gates. Other R2 upload families still require registry adoption. No global cleanup switch or tenant deletion is enabled.
