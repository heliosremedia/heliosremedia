# Packet 66: Media collection mutation fencing

Reorder and bulk category moves previously trusted access and destination reads made before their write transaction. Their transactions now lock current editor/session authority and the owned project, then lock project media in stable ID order. Bulk moves re-read the active owned destination service under a share lock and derive the saved category and response from that current record. Missing selected media returns a bounded 404; a changed reorder collection retains its 409 contract.

The existing two-pass reorder, complete collection requirement, request-order bulk placement, hero removal and project-service association semantics remain. The project lock serializes these actions with the previously qualified creation and update-asset paths. This does not assert that every media writer already participates: explicit hero/social-image actions and deletion still require their own qualification.

Both-company HTTP/PostgreSQL qualification covers foreign media/service rejection and fourteen observed database-wait races across revocation, demotion, session version and destination archival. A temporary trigger fails after earlier reorder writes or bulk hero removal; media, hero and service-link snapshots must roll back. Concurrent opposite reorders must each complete with one complete final ordering. Successful bulk movement must use the service-derived category, preserve requested order, remove the previous hero and create exactly one owned destination association. Foreign company media remains unchanged.

The harness uses disposable PostgreSQL, synthetic sessions and the existing explicit no-network provider substitutions. No provider object is fetched, deleted or transferred by these actions. Trigger/function cleanup and global schema/index/access postflight remain required. This is not hosted, CDN, Neon or Helios production parity evidence. No schema migration, credentials or production operation. Phase 1 remains open; production ON HOLD.
