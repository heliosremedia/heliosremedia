# Packet 83: invitation transaction admission

The lifecycle audit found three identity entry points beyond Packet 81's common account-edit guard. Invitation creation and revocation read a session before issuing direct writes; invitation acceptance claims a token without checking the workspace. Consequently an already-admitted request can outlive a suspension or role change, and a suspended workspace can still acquire a new account through an old invitation.

Creation and revocation now use the current locked administrator guard inside the same transaction as invitation writes. Creating an OWNER invitation rechecks the current OWNER role; an earlier session role cannot authorize it after demotion. Replacement-token creation and revocation of previous pending invitations are atomic. A failed replacement insert leaves old invitations valid.

Acceptance locks the hinted workspace, requires active lifecycle state, then locks and rereads the invitation's current token/workspace/expiry/revocation/acceptance binding. New identity and membership use that current row, not stale pre-transaction invitation fields. Existing single-use token, role, password and membership semantics remain. This packet does not redefine whether a still-valid token survives the issuer's later demotion; no new real enrollment or credential operation is performed.

Local route tests reproduce denied current authority, OWNER demotion, atomic replacement failure and suspended/stale invitation acceptance. Disposable Next/PostgreSQL qualification covers both tenant directions and fourteen observed waits: create/revoke during suspension or demotion, OWNER invitation after loss of OWNER, acceptance during suspension and token revocation. Rejections must leave invitation/identity rows and successful audit counts unchanged. A database trigger injects replacement-insert failure to verify rollback. Active acceptance creates exactly the owned account/membership; replay is rejected. Synthetic identities/invitations are removed and original membership rows restored, including timestamps.

Exact-head regression/TypeScript/Chromium, runtime, independent artifact verification and matching merge tree remain required before integration. Other private writers, token-owned referrals, analytics, jobs/provider admissions, safety settlement, backlog and hosted compatibility remain open. Phase 1 OPEN. Production ON HOLD.
