# Studio appearance

The sidebar exposes **Day / Night / System** using native, keyboard-operable radios.
System is the default. A browser-local `helios-studio-appearance` preference persists
across visits and synchronizes across tabs. Storage failure retains the current
session choice. System follows OS changes immediately through CSS, without a reload.
A small pre-content bootstrap applies a saved preference before shell content is
parsed. The website, client portal and email recipient appearance are separate.

## Design contract

- Day: neutral light canvas, white cards, charcoal copy, readable gray secondary text.
- Night: existing Studio treatment remains intact.
- Orange is a restrained selection/focus accent. Green is verified/success; red is error/destructive.
- Controls retain shared geometry, visible focus, and at least 44px appearance targets.
- Template previews, historical email snapshots and photographic overlays have fixed
  artwork colors (`data-studio-fixed-colors`), not app-theme transformations.
- Never use CSS inversion or filters to make a light theme.
- New UI should use shared semantic components/tokens. Legacy utility mappings are
  scoped to Studio and generated by `node scripts/generate-studio-theme.mjs`.
  Regenerate and inspect when adding legacy color utilities. Mapping is a migration
  bridge, not a substitute for reviewing new UI.

## Verification and release gate

`node scripts/verify-studio-appearance.mjs` checks validation/bootstrap/storage fallback,
SSR radio semantics and CSS compilation. `verify-studio-appearance-browser.mjs` runs
synthetic actual-shell hydration, keyboard, reload, live OS, cross-tab, mobile and
pre-hydration checks. GitHub Actions uploads desktop/day/night/mobile screenshots.
These are synthetic, not claims about every live module.

Before release, inspect real populated routes in both themes: dashboard, projects and
media fullscreen, clients, email history/composer, newsletters, referrals, feedback,
events, social studio, settings (including pinned navigator), users and dialogs.
Check focus, hover, placeholders, disabled and success/error states. Confirm fixed
email artwork matches the outgoing template and photos remain unaltered. Review
screenshots and a signed-in preview. Do not deploy until that QA and owner approval.

Current limitation: local browser execution is restricted by the execution environment;
full real-data, cross-module visual verification has not been completed. This change
must remain a draft until hosted browser checks and the above release gate pass.
